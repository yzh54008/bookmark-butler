# 收藏夹清理实录：778 → 386

一次真实的浏览器收藏夹整治记录。结论先行：**问题不是「没整理」，是「导入」把整棵树复制了 4 遍。**

---

## 一、现场

| 项 | 数值 |
|---|---|
| 文件 | `%LOCALAPPDATA%\Microsoft\Edge\User Data\Default\Bookmarks` |
| 体积 | 610 KB |
| 书签总数 | **778** |
| 文件夹数 | 39（最深嵌套 5 层） |
| 收藏栏顶层平铺书签 | **166 条** |
| **去重后唯一网址** | **386** |
| **纯垃圾重复** | **392（50%）** |

166 条散书签平铺在收藏栏上，是「每次找东西都要肉眼扫一遍」的直接原因。

---

## 二、根因：导入残留

文件里有 4 个残留文件夹：

```
从 Microsoft Edge 导入
从 Microsoft Edge 导入 (1)
从 Google Chrome 导入
从 Google Chrome 导入 (1)
```

**每一个内部又套了一层完整的「收藏夹栏」**——也就是说，整棵收藏树被复制了 2~4 遍。

后果：`妙手ERP`、`DeepSeek`、`扣子` 这类常用站，同一个网址**最多存了 6 份**。

### 定位方法

不要靠肉眼看。把整棵树导成带路径的清单，然后按 URL 反向索引：

```python
# 简化的核心逻辑
by_url = {}
walk_tree(root, path=[], cb=lambda b, p: by_url.setdefault(normalize(b.url), []).append((p, b)))
for url, hits in sorted(by_url.items(), key=lambda kv: -len(kv[1])):
    if len(hits) > 1:
        print(len(hits), url, [p for p, _ in hits])
```

`dig.py` 做的就是这件事，输出「按目录看」和「按 URL 看」两套视角——
重复一旦按目录聚类，那 4 个「从…导入」会立刻自己浮出来。

---

## 三、另一个隐藏病因：零宽字符

第一轮诊断我用「标题长度 ≤ 3」筛「异常短标题」，得到 56 条，并写进了报告。

**这是错的。** 那 56 条里是 `MY`、`扣子`、`挡泥板`、`拼多多` 这类**完全正常的短标题**。

用正确口径重新核实：

| 口径 | 真实数量 |
|---|---|
| 真正完全空白 | **0 条** |
| 含零宽 / 格式控制字符污染 | **30 条** |
| 清洗后长度 ≤ 3（正常短标题） | 56 条 |
| 清洗后长度 > 60 | **71 条**（先前报 101，也是被零宽字符撑大的） |

### 教训

**所有长度类指标，必须先剥掉 Unicode `Cf`（格式控制）类字符再算。**

```python
import unicodedata
def clean_title(s):
    return "".join(c for c in s if unicodedata.category(c) != "Cf").strip()
```

零宽字符在浏览器 UI 里渲染不出来，但在文件里是真实存在的字节，
所以它既会让标题「看起来是空的」，也会让长度统计虚高。

## 四、重建方案

原则（来自用户明确要求）：**一条不删，只去重归位。**

### 1. 去重

按**归一化 URL** 分组（剥掉 `www.`、统一协议、去尾斜杠、剥离跟踪参数），
每组保留一条，保留策略：

```
路径最深 → 标题最完整 → 添加时间最早
```

「路径最深」优先，是因为越深的条目通常已经被人工归类过一次，语义更准。

### 2. 按业务域重建目录（13 类）

关键设计：**分类体系跟着「业务怎么用」走，而不是「当初怎么存的」走。**

```
01 OZON运营      （卖家后台 / 前台类目页 / 官方店铺库 / 规则学习 / 其他平台）
02 ERP与选品      （ERP系统 / 选品与数据）
03 货源与采购      （电商货源 / 电子元器件）
04 物流与海外仓
05 支付与财税
06 独立站与域名
07 AI工具与自动化  （对话与模型 / 图像与设计 / 自动化平台）
08 云服务与开发
09 学习资料
10 商务与政务
11 素材工具箱
12 社媒与内容
13 自有服务与内网
```

嵌套深度**封顶 3 层**（收藏栏 + 2 层文件夹），再深就找不到了。

### 3. 标题修复

- 剥除零宽 / 格式控制字符
- 超长标题截断到合理长度
- 完全空白的用域名兜底

### 4. 重算 checksum

见 [`02-Chromium收藏夹文件技术笔记.md`](02-Chromium收藏夹文件技术笔记.md)。

## 六、安装环节真正的坑

### 坑 1：浏览器会「自动复活」

你以为用户关掉浏览器就安全了。实际上——**杀掉 10 个进程后 3 秒，又变成 14 个。**

根因在注册表：

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Run\MicrosoftEdgeAutoLaunch_<hash>
    = msedge.exe --no-startup-window --win-session-start
```

这是 Edge 的「启动增强」。它让「先退出浏览器，再手动跑脚本」这条路**根本走不通**
——脚本刚启动就会检测到浏览器在运行然后中止。

**解法**：一个脚本里完成 `kill → 立即原子替换 → 再 kill`，跟它抢时间窗。

```powershell
for ($i = 1; $i -le 3; $i++) {
    Get-Process msedge -ErrorAction SilentlyContinue | Stop-Process -Force
    Start-Sleep -Milliseconds 400
    try {
        [System.IO.File]::Replace($src, $target, $backup)   # NTFS 原子替换
        if ((Get-FileHash $target -Algorithm MD5).Hash -eq $expectMd5) { break }
    } catch {
        Move-Item $src $target -Force                        # 回退方案
    }
}
```

> ⚠️ `msedgewebview2.exe` 是**别的软件**内嵌的运行时，**不能杀**。
> 只结束 `msedge.exe`。

**怎么判断浏览器真的被关掉了？** 别只看进程数。真正的判据是：

- 所有进程的 `MainWindowHandle -eq 0`（没有可见窗口）
- 主进程命令行带 `--no-startup-window`
- `Last Session` 文件不存在（没有会话可丢）

三者同时成立，杀进程就是零损失。

### 坑 2：PowerShell 5.1 会把中文 `.ps1` 读成乱码

Windows PowerShell 5.1 对**无 BOM** 的 `.ps1` 按系统 ANSI（中文环境即 GBK）解析。
UTF-8 的中文全部变成乱码，`关闭` → `鍏抽棴`，然后直接 `ParserError` 崩掉。

**规则：凡 `.ps1` 含中文，必须存成 UTF-8 带 BOM。**

```powershell
$txt = [System.IO.File]::ReadAllText($p, (New-Object System.Text.UTF8Encoding($false)))
[System.IO.File]::WriteAllText($p, $txt, (New-Object System.Text.UTF8Encoding($true)))
```

并且在下发前用 Parser 预检：

```powershell
$err = $null
[void][System.Management.Automation.Language.Parser]::ParseFile($p, [ref]$null, [ref]$err)
$err.Count   # 必须是 0
```

或者更省事的做法：**让 `.ps1` 的输出全部用纯 ASCII**，绕开整个编码问题。

## 八、附带发现：同步

账户已登录且 `sync.keep_everything_synced = True`，但**当时同步实际处于停用状态**：

- 当日日志中所有数据类型 `Stopped`
- 报 `PERSISTENT_ERROR, EDGE_AUTH_ERROR`（登录凭证失效）
- 最后一次成功同步是好几天前

这**反而是好消息**——不存在云端把垃圾推回来的风险。

### 但要注意

去重时**保留了每条书签的原始 `guid`**。Chromium 的同步引擎正是用 `guid` 作为同步实体标识
（原始文件里没有 `meta_info` 字段，说明走的就是 guid 通道）。

因此当用户之后重新登录恢复同步时，**本地「消失的 392 条」会被识别为删除操作上行同步**，
而不是「云端有、本地没有 → 拉回来」。这就是保留 GUID 的价值。
