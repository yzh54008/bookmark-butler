# 浏览器扩展接入大模型的工程实践

把大模型封装进一个要「给别人用」的浏览器扩展，难点不在调 API，而在这四件事：

1. **Key 怎么存** —— 每个人填自己的，我这边不能碰
2. **提示词怎么组织** —— 不能让模型对着几百条书签乱猜
3. **模型输出不可靠怎么办** —— 幻觉、截断、加围栏、返回臆造目录
4. **没有 Key 怎么验证** —— 总不能每改一行就求人借个 Key

---

## 一、设计取向：分类体系必须是「长出来的」

这是「能不能给别人用」的分水岭。

**错误做法**：把开发者自己的分类规则（比如某电商平台那套）写死进去，然后管这叫「智能」。
换个人用，他的书签会被塞进一堆与他无关的目录 —— 那不叫智能，叫硬编码。

**正确做法**：让模型从**使用者自己的数据**里归纳分类体系。

```
使用者的书签
   ↓ 按域名聚合（几百条 → 几十个域名）
   ↓ 只把摘要交给模型
模型归纳出 6~14 个一级目录
   ↓ 把每个域名指派到一条路径
   ↓ 只对「一个网站多种用途」的条目逐条细判
最终方案 → 预览 → 用户确认 → 执行
```

这样一来，同一个扩展在不同人手里长出来的目录结构**是完全不同的**，而且各自贴合各自的业务。

## 二、分层架构

| 模块 | 职责 | 关键约束 |
|---|---|---|
| `provider.js` | 9 家服务商预设 + 自定义端点；统一 OpenAI 兼容协议 | 自定义地址走**可选权限**运行时申请 |
| `store.js` | 配置读写、Key 掩码 | **只用 `storage.local`，绝不用 `storage.sync`** |
| `client.js` | Chat 请求：重试 / 退避 / 超时 / 取消 / JSON 抽取 / 错误翻译 | 纯函数化，方便注入 mock |
| `prompts.js` | 三阶段提示词 | 提示词与逻辑分离，便于迭代 |
| `planner.js` | 规划流水线（**不依赖任何 chrome API**） | 纯逻辑 → 可在 Node 里端到端测试 |
| `apply.js` | 执行移动、记录操作日志、一键撤销 | **只移动，从不删除** |

> **`planner.js` 刻意不依赖 `chrome.*`** 是整个测试策略的支点：
> 因为它是纯逻辑，所以我能在 Node 里用一个内存版的 `chrome.bookmarks` 桩
> 把整条流水线跑通，**不需要真的装扩展，也不需要 API Key**。

## 三、API Key 怎么存

### 用 `storage.local`，不用 `storage.sync`

这是整个设计里最重要的一条：

```js
// ✅ 正确：只存在本机这个浏览器 profile 里
await chrome.storage.local.set({ aiConfig: cfg });

// ❌ 错误：storage.sync 会把 Key 上传到你登录的云端账号
await chrome.storage.sync.set({ aiConfig: cfg });
```

`storage.sync` 看起来很诱人（多设备同步），但它意味着**用户的 API Key 被上传到云端**。
对一个「填自己的 Key」的工具，这是不可接受的设计。

### 配套细节

- 界面**永不回显完整 Key**，只显示掩码（如 `sk-abc…xyz4`）
- 保存前用一次极小的请求测试连通性，把 `401 / 402 / 404 / 429` 翻译成人话
- Key 只从用户的浏览器**直连**模型厂商，不经过任何中间服务器

## 四、权限：开箱即用 + 最小面

```jsonc
{
  "permissions": ["bookmarks", "storage", "favicon"],
  "host_permissions": [
    "https://api.deepseek.com/*",
    "https://api.openai.com/*",
    "https://api.moonshot.cn/*",
    "https://dashscope.aliyuncs.com/*",
    "https://open.bigmodel.cn/*",
    "https://api.siliconflow.cn/*",
    "https://openrouter.ai/*",
    "http://127.0.0.1/*",          // Ollama
    "http://localhost/*"
  ],
  "optional_host_permissions": ["https://*/*", "http://*/*"]
}
```

- 常用服务商**预授权** → 装完就能用，不用先点授权弹窗
- 任意自定义端点 → 用 `optional_host_permissions`，
  **在用户点击「保存」时**才调用 `chrome.permissions.request()` 申请

关键点是**申请时机**：必须在用户手势（click）的调用栈里发起，否则会抛错。
所以 `ensureOriginPermission()` 是绑定在保存按钮的处理函数里的，不是自动触发的。

## 五、三阶段提示词流水线

直接问模型「帮我把这 386 条书签分类」，结果必然一塌糊涂。原因有两个：**上下文太长**、
**决策量太大**。

所以拆成三阶段，每一阶段都在降低模型的决策难度：

### 阶段 A：归纳体系（只喂摘要）

先把书签**按域名聚合**：

```
386 条书签  →  约 120 个域名
每个域名携带：出现次数、若干代表性标题、是否多用途
摘要体积  ≈ 3500 tokens
```

只把这份摘要交给模型，让它产出 6~14 个一级目录（可带二级）。

**降 token 的本质**：模型的输入规模从「书签数」变成「域名数」。

### 阶段 B：域名分派（决策量 = 域名数）

并发分批，把**每个域名**指派到体系中的一条路径。

因为同一域名下的书签绝大多数应该进同一个目录，所以这一步只需要 120 次决策，
而不是 386 次。省下的不只是钱，还有出错概率。

### 阶段 C：一域多用途逐条细判

只有那些「同一个网站有多种用途」的域名才需要逐条判断。典型场景：

```
ozon.ru/.../汽车用品新热   →  前台类目页（调研用）
seller.ozon.ru             →  卖家后台（干活用）
某 ERP 域名                 →  工具（日常用）
```

这三类东西在「按域名归类」的视角下是一个域名，但业务上完全是三类。
所以这里必须下沉到逐条判断——**并且只对这一小撮条目做，token 花在刀刃上**。

### 兜底复核

所有落到「待整理」的条目**再问一轮**（分小批，避免输出被截断）。

> 这里踩过一个坑：最初只复核「模型完全没给结论」的条目，
> 漏掉了「模型主动把某条丢进待整理目录」的条目——**这两者其实是同一回事**。
> 改成全覆盖复核对所有落入兜底目录的条目生效后，兜底率明显下降。

### 最终兜底

本地规则引擎 → `99 · 待整理`。**绝不乱放**——宁可挂在待整理里让人一眼看到，也不要塞进错误的目录。

## 六、模型输出不可靠的四道防线

### 防线 1：JSON 抽取三层兜底

```
1. 直接 JSON.parse
2. 剥掉 ```json 代码围栏再 parse
3. 取最外层平衡括号片段再 parse
4. 全都失败 → repairTruncatedJson()：按栈补全未闭合的括号/引号，再 parse
```

最后那一步是必需的：模型输出被 `max_tokens` 截断时，JSON 一定是不完整的，
而截断往往发生在最有用的部分之后。

### 防线 2：路径模糊对齐 `coercePath()`

模型经常会：漏写序号前缀（`OZON运营` vs `01 · OZON运营`）、
二级目录名少一个字、用 `/` 或 `>` 当分隔符。

`coercePath()` 做多级模糊匹配，把这些都拉回合法路径。

### 防线 3：合法性断言

对齐之后**必须断言**：所有目标路径都在合法清单（模型自己产出的体系）内。

这一步专治**模型臆造目录**——它会信誓旦旦地指向一个它自己没定义过的文件夹。
断言不通过就不采纳，降级到兜底。

### 防线 4：体系生成失败时的降级

如果阶段 A 就失败了（网络错误、输出截断到无法修复、模型不听话），
**不要整条流水线崩掉**。降级策略：

```
体系生成重试 2 次
   ↓ 仍失败
用本地规则引擎的顶层目录当作体系骨架
   ↓
继续走阶段 B / C
```

这样即使模型完全不可用，「整理」这件事依然能完成——只是质量退化为本地规则水平。

## 七、执行层：只移动，从不删除

```js
// 每一次移动都记录完整的操作日志
{ bookmarkId, fromParentId, toParentId, createdFolderIds: [...] }
```

撤销 = **逆序遍历日志**，把条目移回原父目录，然后清理**本次新创建**的空文件夹。

两个细节：

- 必须**逆序**，否则嵌套移动会乱
- 只清理「本次创建的」文件夹，不能顺手删掉用户原有的空文件夹

---

## 八、隐私：默认少发

- 默认只发**域名 + 标题**，**不发完整 URL**
- 要发完整 URL 必须显式勾选，且卡片中明确警告：URL 可能带订单号、token、会话参数
- 发送前可**展开「将发送的摘要」原文**逐字核对
- 想彻底不出本机 → 选 Ollama + 本地模型

设计原则：**默认值必须是保守的那个**，把「多发数据」变成一次有意识的选择。

## 九、没有 Key 怎么测：mock 服务端 + 内存桩

这是整个项目里最值钱的一块工程实践。

### 做法

1. 起一个**本地 OpenAI 兼容的 HTTP 服务端**（`node:http`，几十行）
2. 在**内存里**实现 `chrome.bookmarks` 的桩（getTree / create / move / remove / update）
3. 把 `planner.js`、`apply.js`、`tidy.js` 用真实数据喂进去
4. 断言全链路结果

### 故障注入（这是关键）

mock 服务端按预设脚本返回四种**真实会遇到**的响应：

| 故障 | 验证什么 |
|---|---|
| `401` | 错误是否被翻译成「鉴权失败，请检查 API Key」 |
| `429` | 指数退避重试是否生效、最终是否成功 |
| ```` ```json ```` 围栏包裹 | JSON 抽取第二层是否生效 |
| JSON 被截断 | `repairTruncatedJson` 是否能补全 |

### 覆盖的断言（共 32 项）

摘要聚类、成本预估、JSON 抽取与修复、错误翻译、全流水线（含 429 重试）、
路径合法性、围栏/截断容错、Key 错误提示、取消是否生效、
以及**执行 386 条移动 → 一键撤销 → 全部回到原目录**。

### 这套测试真抓出了两个 bug

1. **模型返回截断的分类体系会让整条流水线崩掉**
   → 加了体系生成重试 + 降级到本地规则骨架（即上面提到的防线 4）

2. **兜底复核漏掉了一整类条目**（见上面「兜底复核」下的坑）

> ⚠️ mock 场景下 `99 · 待整理` 占比偏高（≈23%），这是 mock 的关键词桶表覆盖不全导致的，
> **不代表真实模型水平**。真实质量必须用自己的 Key 跑一次才算数。

## 十、打包给朋友：防泄漏自检

开发目录里往往躺着**用真实数据生成的样例文件**（比如为了让界面能预览而生成的
`mock-data.js`，里面就是用户本人的完整书签）。**直接把文件夹拷给朋友 = 把书签送出去了。**

所以打包脚本要做三件事：

1. 排除 `dev/`、日志、测试产物
2. 自动摘掉 HTML 里对调试垫片的引用（否则别人加载会报错）
3. **内置防泄漏自检**：一旦在暂存目录里发现 `dev/` 或样例文件，**直接中止打包**

另外，脚本应当校验「排除规则是否真的生效」，而不是假设生效——
最终产物解压后要重新核对文件清单，确认没有意外文件混进去。

## 十一、总结：几条可以复用的原则

1. **能力要长在用户数据上，不要长在开发者假设上**
2. **密钥存 `local` 不存 `sync`**，掩码回显，最小权限，运行时申请
3. **降低模型决策量**比提高模型能力更有效（聚合 → 分派 → 细判）
4. **对模型输出永远做合法性断言**，不信它就信校验
5. **每一层都要有降级路径**，模型不可用时功能依然可用
6. **纯逻辑与平台 API 解耦**，否则你永远测不了它
7. **破坏性操作要有日志、要能撤销、要默认不删除**
8. **默认值取保守的那个**（少发数据、只移动不删除、先预览再执行）
